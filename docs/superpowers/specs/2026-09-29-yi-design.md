# yi: local usage statistics and isolated harness migration

## Scope

Build the `yi` Claude Code plugin in the `claude-plugin-yi` repository. Count observable manual and automatic skill and command invocations locally. Aggregate component counts by source plugin. Show counts in descending order, with names as stable tie-breakers. Support multiple selected source items and multiple targets. Targets are Amp Code, Codex CLI, OpenCode v2 (`@opencode/cli`), and Pi.

Use Python and SQLite for the local core. Do not require a remote service or model for counting or conversion. Do not store prompt bodies, arguments, credentials, or full transcripts in the usage database.

## Invocation collection

Record successful Skill tool invocations through PostToolUse. Use command expansion events for observable slash commands. Verify event fields against the installed Claude Code CLI before selecting the deduplication key. Correlate overlapping observations of one invocation rather than counting each hook as a separate invocation. Distinct calls to the same skill in one session must remain distinct.

Do not distinguish manual and automatic invocation sources in the public statistics. Plugin totals aggregate identified component invocations; loading a plugin does not count as execution. Document commands that Claude Code does not expose. Do not claim complete built-in-command coverage.

Provide explicit historical import. Read local session records only when requested. Support known transcript formats, report unsupported records, and make repeated imports idempotent. Historical imports and live collection must share deduplication rules where stable identifiers exist. Report records that cannot be safely reconciled instead of silently inflating totals.

Store the database outside the source repository and migration artifacts. Use SQLite transactions, bounded lock waits, and restrictive file permissions. Collection failures must not block the user's normal Claude task; report diagnostic failures without recording sensitive input.

## User commands

Expose two user-facing skills: `/yi:usage` and `/yi:migrate`. The usage skill shows invocation counts in descending order, grouped by plugin or component, without starting migration.

The migration flow shows ranked usage, supports multiple source items and targets, previews changes, generates Git-managed artifacts, and reports verification results. Offer explicit historical import within this flow when requested. Accept the output root as an argument or saved local configuration. Offer installation as an explicitly confirmed step after artifact inspection, not a separate slash command.

The skill calls private local helper operations for collection, queries, import, generation, checks, and installation. These operations are implementation interfaces, not additional user commands. Support explicit item IDs and target arguments for repeatable migration. Interactive selections must support more items than one small fixed menu. Cancelled selections must not change files.

## Managed artifact directory

The user can configure the output root. Initialize one Git repository at that root, not one repository per target. Place each target's isolated HOME beneath a distinct target directory. Keep manifests and compatibility reports alongside generated content.

Example layout:

```text
<artifact-root>/
  .git/
  .gitignore
  ampcode/home/
  codex/home/
  opencode-v2/home/
  pi/home/
  manifests/
  reports/
```

HOME, XDG paths, and target-specific configuration roots must resolve within the selected target directory during checks. Do not inherit real user configuration or credentials by default. The directory provides configuration isolation, not an operating-system security sandbox. Running source scripts or MCP servers requires an explicit execution decision.

Exclude runtime caches, logs, credentials, and usage data from Git. Track generated file ownership and hashes. Detect path traversal, escaping symlinks, collisions, and user modifications before writes. Never recursively clear an arbitrary configured root. Never stage unrelated files.

## Git boundary

Initialize a Git repository in a fresh artifact root so generated changes remain inspectable. Generation does not require Git identity, signatures, staging, commits, or a clean unrelated working tree. Use content ownership to refuse conflicting writes. Leave commit granularity, signing, and publishing to the user's Git workflow.

An unchanged conversion reports no file changes. Reviewed manual resources remain protected from generation even after their hashes are accepted for installation. Shared rendered configuration has one target-level owner; plugin manifests retain only their own contributions and exclusive resources.

Development commits for this project follow the configured identity and signature requirements; that policy does not become a runtime migration dependency.

## Conversion contract

Inventory the selected plugin's skills, legacy commands, hooks, agents, MCP configuration, and referenced local resources. Preserve required resource relationships and deliberately translate plugin-root references. Selecting a plugin selects its component inventory; selecting a component selects its required resources, not unrelated plugin capabilities.

Each target adapter produces deterministic files and per-component results:

- converted: a supported translation was generated;
- blocked: no equivalent translation is supported;
- unverified: runtime evidence is incomplete.

Do not convert enforceable permissions or security hooks into advisory prompt text. Do not silently omit unknown fields that affect behavior. Avoid embedding source secrets in generated configuration; preserve supported environment-variable references and report missing credential setup.

For blocked components, report source paths, the incompatible behavior, and the behavior that needs verification. Recommend using the destination harness to assist further migration inside the managed artifact repository. yi does not invoke a model to rewrite components. A report with blockers must not claim complete migration success.

Keep generation, checking, and installation separate. Installing only compatible components requires an explicit partial-selection decision. Before installation, preview destination changes and conflicts. Preserve source Claude files. Do not automatically execute installed scripts or start MCP services.

## Native verification

Distinguish format validation, native CLI discovery/loading, and behavioral verification. Record exact CLI versions. A successful file copy, version command, or configuration parser is not proof of functional parity.

Observed test baselines: Claude Code 2.1.283, Codex 0.157.1, OpenCode 2.0.19, Pi 0.87.1, and Amp 0.0.1790683256-gc25f8e. Codex skill discovery and disabled MCP parsing have runtime evidence. Pi skill, prompt-template, and extension-command discovery have runtime evidence. Amp module loading has evidence, but hook behavior remains unverified. OpenCode configuration parsing has evidence; resource activation requires further verification.

Install missing test CLIs through mise. Use the official Amp installation script. Do not replace OpenCode v2 with its v1 package. Do not upgrade existing CLIs without a reason and explicit scope.

## Acceptance tests

Write behavior-first tests with descriptions beginning with `user` and Given/When/Then scenarios. Use actual isolated files, SQLite databases, Git repositories, and subprocesses. Do not mock internal method calls.

Cover manual and automatic call collection, duplicate events, distinct repeated calls, concurrent writes, stable ranking, multi-selection, historical import, malformed data, path escapes, symlinks, collisions, modified artifacts, credential exclusion, generation without Git identity or staging, ownership conflicts, no-op migration, partial results, and installation conflicts. Add regression scenarios for review findings.

Use harmless native harness fixtures for discovery checks. Test hook behavior only when the fixture's execution is explicitly controlled. Do not run arbitrary installed user plugins to validate the converter.

Run local `code-review medium` and `simplify`, resolve verified findings, and rerun affected and full checks. The `thermos` skill requires direct user invocation in this environment; report that gate accurately. Follow Conventional Commits, required attribution, and signed commits. Do not commit local memory, credentials, or probe output.
